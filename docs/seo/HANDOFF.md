`.live-steps > p` (10px→12px), `.live-section-heading` (11px→12px), `.live-client-nav > button` labels (10px/9px base+mobile→12px, both matching the existing 12px used elsewhere in the same `.live-*` demo family, not a new value) — all in `apps/web/src/app/marketing.css`. `.payment-window` (the `Payments()` preview in `product-scenes.tsx`) got the same `role="img"` + `aria-label` treatment already used by the other static previews (`Review`, `InboxPreview`, `VaultPreview`) — it was genuinely noninteractive with zero real controls, so this follows the existing pattern rather than inventing a new one. Verified three ways, not just by Lighthouse score: `audit:responsive 360 1280` is 0 failures across all 21 routes, `tsc`/biome clean, and a direct headless-Chrome screenshot of the homepage nav, `/features/check-ins`'s Responses card and `/features/payments` confirms no visual change beyond the font-size bump (screenshots at `/private/tmp/phase8-*-viewport.png`, not committed).

Separately, Phase 7's final measurement surfaced a desktop-only `heading-order` failure not in the original small-text list: `Review()`'s decorative Development-tab mock (used on the homepage and `/features/check-ins`) had a literal `<h4>Responses</h4>` inside a `role="img"` wrapper — a false heading-order skip in the page's real DOM outline, even though AT never actually reaches it (the `role="img"` ancestor collapses the whole subtree to one `aria-label` for assistive tech; Lighthouse's static `heading-order` audit doesn't know that). Changed to `<p className="replica-responses-heading">`, with the CSS selector renamed to match (and scoped as `.replica-responses > .replica-responses-heading` with an explicit `color: inherit` — the plain class alone would have lost a specificity fight to the pre-existing `.replica-responses p` rule meant for the response body text, which would have silently given the heading the wrong color and margin). Lighthouse accessibility is now 100 on both mobile and desktop homepage.
