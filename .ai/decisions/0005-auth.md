# 0005 — Authentication architecture
2026-09-11 · Status: accepted

## Context
Two very different audiences. Coaches sign up on desktop and are the buyers. Clients are
on budget phones, are invited, and every point of friction costs activation — which is the
metric the business is judged on. India is phone-first, and we're building WhatsApp
integration regardless.

## Decision
**Passwordless-first, provider-agnostic.**

```
user            identity: name, email?, phone?, verification timestamps
auth_identity   one row per login method — password | google | apple | phone
                UNIQUE(provider, provider_uid)
auth_challenge   OTP codes: purpose, code_hash, expires_at, consumed_at, attempts, ip
session          opaque token, revocable
```

Signup — manual: name + phone → WhatsApp OTP → email (unverified) → done.
Signup — OAuth: email + name from provider → phone → WhatsApp OTP → done.
Whichever identifier you didn't arrive with, step two collects. **Phone is always verified;
email never is at signup** — optional later from settings.

**Signup progress is derived, not stored:** `phone_verified_at IS NULL` → step 1;
`email IS NULL` → step 2; else complete.

**Sessions are opaque tokens, not JWTs.** httpOnly, Secure, SameSite=Lax, scoped to
`.traiv.app`. Rotate on privilege change.

**Clients do not self-signup.** They arrive via a coach's invite link bound to an existing
`client` row.

Dev bypass: user-picker gated on `NODE_ENV !== 'production'` **and** `AUTH_DEV_BYPASS=true`,
plus a boot assertion that hard-crashes if both production and bypass are true.

## Consequences
- Adding Apple or another provider is a row type, not a migration.
- Revocation is immediate — required for removing staff and ending impersonation.
- WhatsApp OTP is effectively free per message; no DLT registration needed, unlike SMS.
- Depends on the WhatsApp integration existing before signup can work. **Dev bypass and a
  console OTP transport are required to build anything before that lands.**
- No WhatsApp means no signup. SMS fallback is deferred — accepted risk.

## Alternatives
**Email + password only** — rejected: forces a password on clients, which costs activation.
**JWT sessions** — rejected: cannot be revoked, and revocation is a hard requirement here.
**Supabase Auth** — rejected: would override this model.
